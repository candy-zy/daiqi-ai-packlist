## 1. 背景与问题

用户使用共享表格准备旅行时，通常遇到三个问题：

1. 通用清单与个人实际情况不一致，出现大量无关物品。
2. 团队知道“谁有相机”，但不知道“谁愿意带相机”，设备拥有与分工承诺混在一起。
3. 用户每次旅行都要重新删改同一批物品，系统没有学习其稳定习惯。

个人中心的目标不是增加一个传统账号页，而是维护能够直接改善清单质量的长期信号：

- 我平时怎样出行。
- 我拥有哪些可用于团队分工的设备。
- 哪些个人提醒只应该自己看到。
- AI 为什么推荐某件物品或建议某个人携带。

---

## 2. 产品目标

### 2.1 用户目标

- 首次使用 30 秒内完成偏好设置。
- 新建旅行后，清单明显更符合个人习惯，减少重复删除。
- 队友可以知道谁拥有团队设备，但设备所有者仍可决定是否携带。
- 用户理解“为什么出现这件物品”和“为什么推荐我来带”。

### 2.2 业务目标

- 提升创建队伍后的清单有效率。
- 提升 AI 推荐加入率。
- 降低用户创建清单后 5 分钟内的删除率。
- 提升团队物品在出发前完成分工的比例。

### 2.3 非目标

- 不做旅游路线、景点、酒店或餐厅攻略。
- 不根据性别直接推断化妆、护肤、生理用品等需求。
- 不把“有设备”自动等同于“我来带”。
- 不允许 AI 未经确认直接修改团队分工。
- 不在 MVP 中建立复杂社交主页、动态或关注关系。

---

## 3. 用户与核心场景

### 3.1 核心用户

- 18–35 岁，2–4 人朋友结伴出行。
- 行程 2–10 天，以城市游、拍照、演唱会、短途度假为主。
- 当前常用微信群聊、备忘录或共享表格准备物品。

### 3.2 关键场景

| 场景 | 用户意图 | 系统行为 |
|---|---|---|
| 首次注册 | 快速告诉系统自己的习惯 | 提供少量可跳过的多选项 |
| 新建旅行 | 生成适合本人的基础清单 | 合并固定物品、偏好规则和旅行条件 |
| 团队分工 | 知道谁有某个设备 | 显示设备拥有者，并发起“推荐携带”确认 |
| 修改偏好 | 新买相机或不再化妆 | 更新未来旅行；当前旅行只增量提示，不擅自删除 |
| 出发核对 | 只看自己要带的物品 | 展示个人自备物品和已确认认领的团队物品 |

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| 固定基础物品 | 大多数用户在某类旅行中都需要的物品，不依赖大模型生成 |
| 条件物品 | 由国际/国内、天气、天数、交通方式等确定性条件触发 |
| 个性化物品 | 由用户主动选择的习惯、健康提醒或设备触发 |
| 个人自备 | 每位成员都应分别准备，只能本人核对，队友可查看状态但不能替其勾选 |
| 团队物品 | 一人或多人携带即可，需要认领或分工确认 |
| 设备拥有 | 用户声明自己拥有某设备，是推荐分工的信号，不是携带承诺 |
| 已认领 | 用户明确点击“我来带／我也带”或确认 AI 分工卡后的承诺 |
| AI 缺口建议 | 固定规则和个性化规则执行后，AI 补充的最多 2 件未包含物品 |

---

## 5. 产品原则

1. **确定性规则优先于大模型**：身份证、护照、充电器等由规则产生，避免成本和不稳定性。
2. **显式偏好优先于人口属性推断**：用户选择“会化妆”，系统才增加相关物品。
3. **拥有不等于携带**：设备库只产生推荐，不直接写入 `item_assignments`。
4. **个人隐私分级**：健康偏好仅本人可见；设备信息可向同一旅行队伍展示。
5. **当前旅行只增不暗删**：修改偏好后，系统可以建议新增，不自动删除用户已经确认过的物品。
6. **团队动作必须确认**：AI 识别出的分工先成为候选卡片，确认后才改变清单。
7. **少而准**：首轮 AI 建议最多 2 件，个人中心首屏不超过 11 个选择项。
8. **可解释**：每个个性化新增或分工建议都保留 `reason_code` 和可读理由。

## 6. 信息架构与入口

### 6.1 首次使用

```text
注册/登录
  → 创建旅行前页面
  → “我的出行偏好”卡片
  → 个人中心弹窗
  → 保存
  → 输入目的地
  → 生成清单
```

首次偏好设置可跳过。跳过时使用基础清单，不阻断创建旅行。

### 6.2 已进入旅行

- 准备清单页：点击右上角自己的头像进入个人中心。
- 出发核对页：头像仍用于切换查看成员清单，不进入个人中心，避免一个入口承担两个动作。
- 正式 App 的全局“我的”页可作为二级入口，但 MVP 不增加底部导航。

### 6.3 个人中心页面结构

1. 头像与昵称。
2. 我会怎么出行。
3. 我有这些设备。
4. 本次影响预览。
5. 隐私说明。
6. 保存并更新清单。

## 8. 个性化清单决策策略

### 8.1 总体管线

```text
固定基础模板
  + 旅行硬条件（境内/境外、天气、天数、交通方式）
  + 用户显式偏好
  + 用户设备库
  + 队友设备与当前分工
  → 规范化、同义词去重、分类
  → 确定个人自备 / 团队候选
  → 生成分工建议（不自动认领）
  → AI 最多补充 2 个规则未覆盖的缺口
  → 用户确认
```

### 8.2 第一层：固定基础模板

固定模板不调用大模型，并按旅行范围区分：

| 条件 | 物品 | 类型 |
|---|---|---|
| 所有旅行 | 身份证、银行卡/现金、充电器、充电宝、基础换洗衣物、牙刷、牙膏 | 个人自备 |
| 境外旅行 | 护照/签证、流量卡或漫游方案 | 个人自备 |
| 有托运行李 | 行李牌、液体密封袋 | 个人或团队候选 |

说明：固定模板是候选基础清单，用户仍可删除不适用物品。删除属于本次旅行决策，不回写为长期偏好，除非用户主动选择“以后不再推荐”。

### 8.3 第二层：旅行条件规则

| 输入信号 | 例子 | 规则输出 |
|---|---|---|
| `destination_country` | 韩国 | T-money、流量卡候选；不生成景点攻略 |
| `international=true` | 境外 | 护照/签证、转换插头检查 |
| `weather.rain_probability >= 40%` | 有雨 | 雨伞/雨衣候选 |
| `temperature_min <= 5°C` | 低温 | 外套、围巾等候选 |
| `duration_days >= 5` | 5 天以上 | 增加换洗数量提醒，不重复创建同名物品 |
| `activity=concert` | 演唱会 | 应援物料可进入“其他/活动用品”扩展分类，MVP 后续支持 |

### 8.4 第三层：个人偏好规则

- 用户主动选择后，关联物品进入个人候选池。
- 已存在同名或同义物品时不重复创建，只追加 `reason_code`。
- 健康偏好生成的物品默认个人自备、仅本人收到提醒。
- 偏好取消后：
  - 对未来新旅行立即停止触发。
  - 对当前旅行不自动删除；在物品详情显示“偏好已取消，可手动删除”。

### 8.5 第四层：设备与团队分工

设备拥有者用于计算“适合谁带”，但不直接认领：

```text
若设备只有 1 位成员拥有：向该成员展示“推荐你来带”确认卡
若设备有多位成员拥有：按可用状态、当前负担和本人意愿排序候选
若无人拥有：物品进入待分工，允许讨论、购买或删除
```

推荐排序：

1. 本次明确设置为可用。
2. 用户主动勾选“愿意携带此类设备”。
3. 当前已认领团队物品数量较少。
4. 设备所有者本人，而不是临时借用者。

不使用黑箱综合分数直接做决定。后端可保存排序原因，但最终只输出可解释的 1–2 位候选人。

### 8.6 第五层：去重与冲突处理

规范化规则：

- 去除空格、连接符、全半角括号和大小写差异。
- 维护同义词表，例如“移动电源=充电宝”“SIM 卡=流量卡”。
- “充电器”在当前产品定义中已包含常规充电线，不再单独生成“充电线”。
- 同名物品允许多人携带，但清单中只保留一行，通过多个携带者头像表达。
- 用户删除物品后，本次会话内加入 `suppressed_item_ids`，AI 不得立刻重新推荐。

### 8.7 输出动作类型

| action_type | 系统动作 | 是否需要确认 |
|---|---|---:|
| `ADD_PERSONAL_BASE` | 加入每人自备基础项 | 首次生成无需逐项确认，可删除 |
| `ADD_PERSONAL_PREFERENCE` | 根据本人显式偏好加入个人项 | 保存偏好时整体确认 |
| `ADD_TEAM_CANDIDATE` | 加入团队待分工池 | 是，用户可删除 |
| `SUGGEST_ASSIGNEE` | 推荐某成员携带 | 必须确认 |
| `AI_GAP_SUGGESTION` | 展示最多 2 个 AI 缺口卡片 | 点击加入后生效 |

## 9. 当前旅行应用规则

用户点击“保存并更新清单”后：

1. 保存长期偏好。
2. 重新计算当前旅行的增量候选。
3. 仅新增当前清单中不存在的物品。
4. 不修改已勾选、已认领、已留言的物品。
5. 不自动删除因旧偏好产生的物品。
6. 展示一次结果摘要，例如“已补充 2 件，生成 1 条分工建议”。
7. 所有新增均写入 `source_type` 与 `reason_code`，支持解释和撤销。

## 10. AI 功能一：个性化目的地缺口推荐

### 10.1 调用时机

- 新建旅行并完成基础规则合并后调用一次。
- 用户显著修改目的地或偏好后，可手动刷新；自动调用需 5 分钟去抖。
- 两条建议均加入或拒绝后，卡片区域折叠为“AI 已检查，本次没有新的明显漏项”。

### 10.2 输入

```json
{
  "trip": {
    "destination": "韩国 · 首尔",
    "duration_days": 5,
    "international": true,
    "weather_summary": "有雨，2–9℃"
  },
  "profile_signals": ["喜欢拍照", "重视护肤", "有相机"],
  "existing_items": ["身份证", "护照 / 签证", "相机"],
  "suppressed_items": ["转换插头"]
}
```

不得向模型发送用户姓名、邮箱、队友聊天全文或健康诊断文本。健康偏好只转为最小化标签。

### 10.3 System Prompt 基线

```text
你是旅行物品清单助手，不做路线、景点、酒店或餐厅攻略。
只推荐容易被忽略、但对目的地和用户偏好确实实用的随身物品。
排除已有物品、同义项和用户明确删除的物品。
最多返回 2 个；名称短，理由具体，不制造焦虑。
偏好用于提高相关性，但不得基于性别或人口属性推断需求。
```

### 10.4 结构化输出

```json
{
  "suggestions": [
    {
      "catalog_key": "t_money",
      "name": "T-money 交通卡",
      "category": "证件与钱财类",
      "scope": "personal_each",
      "reason": "首尔公交、地铁和便利店都能使用。",
      "reason_codes": ["DESTINATION_KR", "MISSING_FROM_LIST"],
      "confidence": 0.91
    }
  ]
}
```

### 10.5 后处理

- JSON Schema 校验失败：丢弃模型结果。
- 低于置信阈值 0.65：不展示。
- 与目录/已有物品重复：不展示。
- 少于 2 条：用规则候选补齐；没有合格候选则缩短卡片区域。
- 超时 3 秒：返回目的地规则兜底，不阻断创建队伍。

## 11. AI 功能二：聊天分工识别

### 11.1 两类聊天场景

1. **物品留言**：从物品入口打开，天然绑定 `trip_item_id`，不需要 AI 归类。
2. **团队聊天**：自由交流，由 AI 识别潜在清单动作并生成确认卡。

### 11.2 需要识别的动作

| 场景 | 示例 | 结构化候选 |
|---|---|---|
| 指派 + 同意 | A：“充电宝你带吧” B：“好” | B 携带充电宝 |
| 自我认领 | B：“相机我来带” | B 携带相机 |
| 取消携带 | B：“转换插头我不带了” | 移除 B 的携带关系 |
| 多人携带 | A：“雨伞我们都带一把吧” B：“可以” | 相关成员分别携带雨伞 |
| 新增物品 | A：“要不要加个行李牌” | 新增候选，需确认 |
| 模糊表达 | “到时候再说” | 不生成动作 |
| 否定 | “不用我带相机” | 不能误识别为认领 |
| 条件同意 | “如果你不带我就带” | 状态 `needs_clarification`，不自动确认 |
| 多物品一句话 | “我带相机和自拍杆” | 拆为两个候选动作 |

### 11.3 服务端输出

```json
{
  "candidates": [
    {
      "action": "ASSIGN_ITEM",
      "item_id": "item_123",
      "target_user_id": "user_b",
      "evidence_message_ids": ["msg_8", "msg_9"],
      "status": "awaiting_confirmation",
      "confidence": 0.94
    }
  ]
}
```

### 11.4 确认逻辑

- 明确指派只有在目标用户表达同意后，才向目标用户展示确认卡。
- 自我认领可立即展示本人确认卡，不替用户直接修改。
- 确认卡紧跟触发同意消息之后展示，不统一堆到聊天末尾。
- 同一 `item_id + target_user_id + action` 在 10 分钟内保持幂等。
- 用户点击“我来带”后写入分工；“我不带”只拒绝候选，不删除其他人的分工。
- 候选物品已被删除时，卡片失效并提示“物品已不在清单中”。

## 12. 交互与状态

### 12.1 个人中心

| 状态 | 表现 |
|---|---|
| 初次进入 | 使用登录昵称，所有选项未选；展示“可跳过” |
| 已有偏好 | 已选项使用绿色勾选和描边，顶部显示已选数量 |
| 无任何选择 | 影响预览显示“暂不增加个性化提醒” |
| 保存中 | 主按钮 loading，禁止重复提交 |
| 保存成功 | 关闭弹窗，展示 3 秒结果摘要，可撤销本次新增 |
| 保存失败 | 保留用户选择，按钮恢复，提示重试 |
| 网络离线 | 保存为本地草稿，不显示为已同步；恢复网络后主动确认同步 |

### 12.2 无障碍要求

- 所有选项使用真实 `button` 与 `aria-pressed`。
- 关闭按钮有明确辅助名称。
- 字体放大 200% 时卡片内部可滚动，底部保存按钮可访问。
- 不只依靠颜色表达选择状态，必须同时显示勾选。
- 敏感偏好不能出现在锁屏推送文案中。

## 13. 数据模型

### 13.1 `users`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | text PK | 平台稳定用户 ID |
| `display_name` | text | 展示昵称 |
| `avatar_url` | text null | 头像 |
| `created_at` | integer | Unix ms |
| `updated_at` | integer | Unix ms |

### 13.2 `user_preferences`

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | text FK | 用户 |
| `preference_key` | text | 枚举键 |
| `enabled` | integer | 0/1 |
| `visibility` | text | `private` / `team` |
| `updated_at` | integer | 更新时间 |

唯一索引：`(user_id, preference_key)`。

### 13.3 `user_inventory`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | text PK | 设备记录 |
| `user_id` | text FK | 所有者 |
| `catalog_item_id` | text FK | 目录物品 |
| `owned` | integer | 是否拥有 |
| `default_available` | integer | 默认是否可用于旅行 |
| `note` | text null | 例如“自拍杆较短” |
| `updated_at` | integer | 更新时间 |

### 13.4 旅行与清单核心表

- `trips(id, owner_user_id, destination, start_date, end_date, status, created_at)`
- `trip_members(trip_id, user_id, role, joined_at)`
- `catalog_items(id, canonical_name, category, default_scope, aliases_json, active)`
- `trip_items(id, trip_id, catalog_item_id, custom_name, category, scope, source_type, reason_codes_json, deleted_at)`
- `item_assignments(id, trip_item_id, user_id, status, source, confirmed_at)`
- `item_checks(trip_item_id, user_id, checked, checked_at)`
- `item_notes(id, trip_item_id, user_id, content, created_at)`
- `messages(id, trip_id, user_id, content, created_at)`
- `ai_suggestions(id, trip_id, user_id, payload_json, status, created_at)`
- `ai_action_candidates(id, trip_id, action, item_id, target_user_id, evidence_json, confidence, status, created_at)`

### 13.5 数据约束

- 所有旅行写操作必须校验当前用户属于 `trip_members`。
- `item_checks` 只能由对应 `user_id` 修改。
- 团队成员可以读取同队设备库中 `visibility=team` 的记录。
- 健康偏好不返回给队友 API。
- 删除物品使用软删除，保留撤销和审计能力。

## 14. API 契约

| Method | Path | 用途 |
|---|---|---|
| GET | `/api/me/profile` | 获取个人资料、偏好和设备库 |
| PUT | `/api/me/profile` | 更新昵称和偏好，返回影响摘要 |
| PUT | `/api/me/inventory` | 批量更新设备拥有与默认可用状态 |
| POST | `/api/trips` | 创建旅行并生成基础清单 |
| POST | `/api/trips/:id/personalize` | 将最新偏好增量应用到当前旅行 |
| GET | `/api/trips/:id/items` | 获取有权限的清单 |
| POST | `/api/trips/:id/ai-suggestions` | 获取最多 2 条 AI 缺口建议 |
| POST | `/api/trips/:id/messages` | 发送团队聊天消息 |
| POST | `/api/trips/:id/ai-actions/extract` | 从增量消息识别动作候选 |
| POST | `/api/ai-actions/:id/resolve` | 接受或拒绝候选动作 |

### 14.1 更新个人资料请求

```json
{
  "display_name": "小林",
  "preferences": {
    "photo": true,
    "skincare": true,
    "motion": false
  },
  "inventory": {
    "camera": { "owned": true, "default_available": true },
    "power_bank": { "owned": true, "default_available": true }
  },
  "apply_to_trip_id": "trip_123"
}
```

### 14.2 响应

```json
{
  "profile_version": 8,
  "impact": {
    "added_items": ["SD 卡"],
    "assignment_suggestions": ["相机"],

  }

```

服务端必须以 `profile_version` 或 ETag 处理并发更新，避免多设备覆盖。

## 15. 实时同步

偏好本身不需要广播给所有队友；只广播其产生的团队可见结果：

- `inventory.updated`：设备可用性改变。
- `trip_item.created`：新增团队候选物品。
- `assignment_candidate.created`：出现分工建议。
- `assignment.updated`：用户确认或取消携带。

健康和私密习惯不得进入 WebSocket/实时事件的公共 payload。

## 16. 权限与隐私

| 数据 | 本人 | 同队成员 | 系统/AI |
|---|---:|---:|---:|
| 昵称、头像 | 读写 | 读 | 最小化使用 |
| 普通出行偏好 | 读写 | 不展示 | 仅标签化使用 |
| 健康偏好 | 读写 | 不可见 | 仅用于本人清单，不进入聊天分析 |
| 设备拥有与可用 | 读写 | 可读 | 用于分工推荐 |
| 是否已认领 | 读写本人 | 可读 | 用于去重和负担判断 |

用户删除账号时，应删除个人偏好与设备库；历史旅行中的显示名称可匿名化为“已退出成员”。

## 18. 验收标准

### 18.1 个人中心

- [ ] 首次创建旅行前可打开个人中心，未设置也可继续。
- [ ] 准备清单页点击自己的头像可再次打开。
- [ ] 出发核对页头像保持成员清单切换功能。
- [ ] 昵称限制 1–20 字，空值保存时回退登录昵称。
- [ ] 习惯和设备均支持多选、取消和键盘操作。
- [ ] 健康偏好在任何队友接口中不可见。
- [ ] 保存失败不丢失当前编辑内容。
- [ ] 字体放大 200% 时可滚动到所有选项和保存按钮。

### 18.2 个性化规则

- [ ] 同一物品不会因多条规则重复生成。
- [ ] 取消偏好不会自动删除当前旅行物品。
- [ ] 设备拥有不会自动生成已认领状态。
- [ ] 个人物品只能本人核对，队友不能替其勾选。
- [ ] 偏好更新产生的当前旅行变化有摘要和撤销能力。
- [ ] 已删除物品不会在同次 AI 推荐中立即重新出现。

### 18.3 AI

- [ ] AI 推荐最多 2 条，且不与清单或同义词重复。
- [ ] 模型超时或无密钥时返回规则兜底，创建旅行不中断。
- [ ] AI 分工候选有证据消息和目标用户。
- [ ] “我不带”“不用我带”不得误判为认领。
- [ ] 分工确认卡紧跟触发同意消息展示。
- [ ] 未经用户确认不得修改团队分工。

## 19. 异常与边界情况

1. 用户在多个队伍中同时旅行：偏好共用，设备可用状态按旅行覆盖。
2. 用户有相机但本次不可带：保留拥有记录，当前旅行 `available=false`。
3. 两人都有相机：展示候选，不默认选择任一人。
4. 用户修改昵称：历史消息保留用户 ID，展示最新昵称。
5. 用户退出队伍：其团队分工恢复待分工，并提醒其他成员。
6. 偏好触发的物品已被用户自定义改名：通过 `catalog_item_id` 和别名去重。
7. AI 返回目录外物品：允许作为 custom item，但必须通过分类和安全校验。
8. 用户拒绝 AI 建议：本次旅行不重复展示；不永久影响其他旅行。
9. 未成年人或敏感健康信息：不要求填写具体疾病或药名，只提供通用提醒标签。

## 21. 上线前 Go/No-Go

满足以下条件才可从“可交互原型”升级为“完整 MVP”：

- 个人资料和偏好可跨设备持久化。
- 至少两个真实账号可加入同一队伍并实时同步。
- 所有写接口做身份与成员权限校验。
- AI 推荐线上真实调用或明确标注规则兜底来源。
- 聊天分工识别运行在服务端，并保留用户确认。
- 刷新页面后清单、留言、认领和核对状态不丢失。
- 通过隐私、可访问性、模型降级和关键流程回归测试。
