# 「带齐」AI 产品岗位简历写法

> 适用于 AI 产品经理、产品经理（AI 应用）、AIGC 产品经理等岗位。以下内容只使用项目中已经落地、可以通过 GitHub 和线上 Demo 核验的事实，不虚构用户量、转化率或商业收入。

## 推荐项目标题

**带齐 DaiQi｜2–4 人旅行行李协作 App｜AI 产品经理（个人项目）｜2026.08**  
产品 Demo：[daiqi-packlist.xuchenyu020412.chatgpt.site](https://daiqi-packlist.xuchenyu020412.chatgpt.site/) ｜ GitHub：[candy-zy/daiqi-ai-packlist](https://github.com/candy-zy/daiqi-ai-packlist)

## 简历一行版

独立完成「带齐」从用户问题定义、交互设计、AI 策略到可用 MVP 的落地，将朋友出行前散落在群聊和共享表格中的行李讨论，转化为可认领、可确认、可追踪的多人共同清单。

## 简历推荐三条

- **产品定义与协作闭环：** 洞察 2–4 人结伴出行中“共享物品重复携带、口头分工易遗漏、手机表格操作成本高”的断点，设计“创建 / 加入队伍—AI 生成清单—多人认领与留言—个人出发核对”完整链路；支持无人认领、单人认领、多人同带、每人自备及临时退回待分工等状态。
- **AI 推荐策略：** 设计“规则预设 + 大模型补漏”混合方案，将标准目的地、日期、后台天气、用户偏好和已有清单拼接为上下文；通过 DeepSeek 结构化输出、同义词归一化、清单去重、境内外规则、低价值物品过滤和 Top 2 展示，解决大模型推荐冗长、重复及场景不匹配问题，并为无有效缺口和模型异常设计明确回退。
- **对话到业务动作：** 设计团队聊天分工识别能力，从对话中抽取物品、负责人、意图、置信度与证据消息，在同意表达后即时生成确认卡；采用 Human-in-the-loop，只有负责人确认后才写回共同清单，并覆盖拒绝、反悔、多物品、模糊表达和幂等去重场景。

## 如果简历还能放第四条

- **产品化落地与体验迭代：** 将概念原型推进为可注册、可组队、可多人协作的线上产品，并围绕认领状态错乱、境内外推荐误判、推荐重复和无结果等 Bad Case 持续迭代；通过状态约束、规则过滤和兜底反馈，让 AI 能力真正嵌入用户任务，而不是停留在独立问答展示。

如果岗位特别关注协作产品，可将第四条替换为：

- **多人协作与一致性：** 设计服务端持久化、版本号控制和近实时同步机制，将认领操作拆为“物品 × 成员”的独立写入；通过乐观更新、冲突检测与状态 rebase，支持多人同时认领或取消同一物品，避免成员操作彼此覆盖。

## 30 秒面试讲述

“这个项目来自一次真实的朋友出行准备。群聊很适合讨论，但‘你带相机，我带充电器’很容易被后续消息淹没；共享表格能记录状态，但手机上缩放和编辑很不顺。我没有做另一个旅游攻略，而是把问题定义为多人协作：先生成共同清单，再让每个人认领，出发前只核对自己的物品。AI 有两处，一处结合地点、日期、天气、偏好和已有清单补 2 个真正缺失的物品；另一处把聊天里的分工提取成结构化确认卡。两处都不让模型直接改共享数据，而是由用户确认后落库。”

## 数据库 Schema：面试时怎么介绍

数据库不是只把整张清单存成一段 JSON，而是围绕“用户—队伍—物品—认领—沟通—AI 确认”拆成 11 张业务表，并用状态快照辅助同步与恢复：

- **用户层：** `users` 保存账号身份，`profiles` 保存昵称、出行偏好和自有设备，让 AI 推荐可以使用个人上下文。
- **队伍层：** `trips` 保存目的地、邀请码、创建者和数据版本；`trip_members` 建立用户与队伍的多对多关系，并记录队长 / 成员角色及最后在线时间。
- **清单协作层：** `trip_items` 保存队伍物品、分类、排序和 AI 推荐理由；`item_owners` 使用“物品 ID + 成员”联合主键记录认领关系，因此同一物品可以没有负责人、由一人负责，也可以被多人同时认领；`item_notes` 保存物品维度、带时间顺序的留言。
- **聊天与 AI 层：** `chat_messages` 保存团队聊天原文；`assignment_proposals` 保存 AI 从对话中抽取的物品、提出者、目标负责人、意图、置信度以及待确认 / 已接受 / 已拒绝状态，实现“AI 建议”和“真实认领数据”分离。
- **同步与一致性层：** `trip_events` 记录每次变更及版本，用于成员增量同步；`trip_snapshots` 保存队伍状态快照，配合 `trips.version` 处理并发覆盖和状态恢复。

最值得在面试里强调的 Schema 决策是：**认领不是 `trip_items.owner_id` 上的单选字段，而是一张独立关系表。** 这使产品能够自然表达“无人带、A 带、A 和 B 都带、A 取消但 B 保留”等真实协作状态，也避免一个人的操作覆盖其他成员。

## 多人共享协作：同步、延迟与并发怎么介绍

当前版本采用的是**服务端持久化 + 版本号控制 + 2.5 秒短轮询**，属于近实时协作，而不是 WebSocket 强实时：

1. 用户认领 / 取消认领时，界面先乐观更新，并立即调用独立的认领接口；留言、聊天和清单编辑等连续操作经过约 `450ms` 防抖后批量保存，减少频繁请求。
2. 其他成员每 `2.5s` 携带本地 `version` 请求一次队伍状态；版本未变化时只返回 `unchanged` 和成员在线状态，版本变化时才返回最新快照。
3. 因此在网络正常时，认领者本人几乎即时看到结果；队友看到更新的理论等待为 `0–2.5s + 网络耗时`，平均约 `1.25s + 网络耗时`。这是机制推导值，尚未作为线上 P95 实测指标写进简历。
4. 每次写操作都通过 `WHERE version = currentVersion` 做乐观并发控制。两个人同时修改时只有一个请求先成功，另一个收到 `409 + 最新状态`；客户端将本人尚未保存的操作 rebase 到新快照后重试，避免静默覆盖。
5. 认领接口以“物品 + 成员”为最小写入单元，并最多重试 3 次，所以 A 和 B 同时认领同一物品时可以保留两人的关系，而不是后写入的人覆盖前一个人。
6. 在线状态通过访问队伍接口时更新 `last_seen_at`；最近 `45s` 内有心跳的成员显示绿点。

产品层面单个队伍限制为 **2–4 人**，所以重点解决的是小队高频协作的一致性，而不是大群在线文档式并发。当前没有完成正式压测，不应声称可支撑具体 QPS 或同时在线人数；更准确的说法是“已实现 4 人队伍的近实时同步和并发冲突治理”。如果后续追求亚秒级同步，可将状态变更通知升级为 WebSocket / Durable Objects，而保留现有版本号和关系表作为一致性底座。

## 适合在面试中重点展示的 3 张图

1. **多人协作清单：** 同时展示无人认领、队友认领、我认领、多人共同携带，证明核心不是个人 Checklist。
2. **AI 聊天分工卡：** 展示“队友提出—用户同意—AI 识别—负责人确认—写回清单”的闭环。
3. **AI Top 2 补漏：** 展示地点 / 日期 / 天气 / 偏好驱动的少量建议，以及加入清单的明确动作。

## 面试可追问的指标设计

- 北极星指标：出发前完成个人待带清单核对的旅行占比。
- 协作指标：建队成功率、邀请加入率、首次分工完成用时、待分工物品占比。
- AI 推荐：采纳率、推荐后删除率、重复率、境内外错误推荐率、响应时延。
- AI 分工：确认率、拒绝率、误触发率、物品 / 负责人抽取准确率、写回成功率。

## 不建议写进简历的表述

- 不写“实时 WebSocket”：当前实现是增量短轮询与在线心跳，更准确的说法是“多人近实时同步”。
- 不写未经验证的用户数、留存、转化率或节省重量百分比。
- 不把它描述成“旅游攻略”或“AI 自动分配行李”；系统预设和补漏，但认领责任由用户决定。
- 不写“AI 自动修改清单”：两项 AI 能力都需要用户确认，强调 Human-in-the-loop 才是产品亮点。
